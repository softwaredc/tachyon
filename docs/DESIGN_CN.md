# 设计与实现

这篇文档讲清楚共享 region 里到底放了什么，以及每个决定是怎么做的。写给要判断"这东西能不能上生产"的人，所以取舍和没做的事也会写。

[English](DESIGN.md) | 中文

## 1. Region 布局

一个 region 是一个 POSIX 共享内存对象（默认 `/dev/shm/tachyon_<name>`），映射到每个参与的进程。同一个 region 在不同进程里的虚拟地址可能不同，这带来第一条铁律：

> **region 里不能放指针，只能放偏移量。**

`TY_PTR(reg, off)` 是把偏移量转成可解引用的唯一合法方式。违反一次——一个 vector、一个虚表、一个绝对地址——就会得到一个"在创建进程里正常、在其他进程里损坏内存"的 region。

```
┌────────────────────────────────────────────────────────┐
│ Region header                                     16 KiB │
│   magic / abi_version / region_size / lease_ns           │
│   ctl_lock       pthread_mutex_t，进程共享 + robust      │
│   bump_off       给 topic 区域用的单调分配器             │
│   procs[128]     pid + heartbeat_ns + state（每项 64B）  │
│   topics[64]     name + state + offset（每项 128B）      │
├────────────────────────────────────────────────────────┤
│ Topic 区域 0                                             │
│   topic header          960 B（计数器各自独占缓存行）    │
│   rings[partitions]     每个 256 B                       │
│   descriptors[partitions][capacity]   每个 16 B          │
│   pool header           1024 B（8 档 × 128 B）           │
│   class 0..7 的 chunk                                    │
│   class 0..7 的租约位图                                  │
├────────────────────────────────────────────────────────┤
│ Topic 区域 1 ...                                         │
└────────────────────────────────────────────────────────┘
```

所有大小都由 `src/internal.h` 里的 `_Static_assert` 钉死。如果哪次改动破坏了它们而没同步提升 `TACHYON_ABI_VERSION`，构建会直接失败，而不是悄悄弄坏已有 region。

## 2. 环形队列：Vyukov bounded MPMC

变长消息放进环形队列，有个绕不开的矛盾：定长槽浪费空间且装不下大消息；紧凑排列要处理回绕和碎片，又慢又复杂。

所以环里只放**描述符**：

```c
typedef struct { atomic_uint64_t seq; uint32_t chunk_idx; uint32_t len; } ty_desc_t;  // 16 B
```

载荷放独立的池。定长元数据拿到想要的缓存行为，变长载荷拿到需要的空间。一条缓存行装四个描述符，顺序消费因此很快。

队列本身用 Dmitry Vyukov 的 bounded MPMC：

- 生产者在 `enq_pos` 上做 `fetch_add`，不用 CAS 混战 `tail`
- 消费者同理操作 `deq_pos`
- 正确性由每槽的序列号提供，生产者不碰别人的槽

初始化把 `descs[i].seq` 设为 `i`；容量必须是 2 的幂，这样 `% capacity` 可以写成 `& mask`。

**必须说清的局限：** 如果一个生产者在"占槽"和"填数据"之间被调度走了，那个槽会卡住直到它回来。队列整体仍在推进，但尾延迟取决于生产者守不守规矩。这是算法固有的，不是没修的 bug。

## 3. 内存池：档位与带代际标记的空闲链表

八个 2 的幂档位：64、256、1024、4096、16384、65536、262144、1048576。每档一个 Treiber 栈，栈顶把索引和 32 位代际 tag 打包进一个 `uint64_t`，用 CAS 原子操作。

```c
head = (tag << 32) | index
```

tag 用来消除 ABA。两个 popper 想拿到同一个节点，中间必须恰好发生 2^32 次操作——按"不会发生"处理。Hazard pointer 更严谨，但每次操作慢约 3 倍；这个取舍写在这里，不藏着。

如果精确档位空了，`ty_loan()` 会向更大的档位借。浪费一点内存，但某个档位很热时吞吐能保住，比直接返回 `NOMEM` 好。

每个 chunk 有 64 字节头（magic、状态、档位、大小、owner pid、租约到期、序列号），所以载荷本身是 64 字节对齐的。

### 全局 chunk 编号

描述符只有 16 字节，要放 `seq`、chunk 索引和长度，没有空间再放"哪个档位"。所以 chunk 在所有档位间**统一编号**，接收时用 `ty_gid_resolve()` 反查。每条消息八次比较，换来一个能一行缓存行装四个的描述符。

## 4. Chunk 生命周期

```
       loan              publish             subscribe         release
FREE ────────► LOANED ────────► PUBLISHED ────────► CONSUMED ──────► FREE
  ▲              │                                      │
  └──── abort ───┘                          崩溃 ───────┘（回收器）
```

顺序很关键，而且开发中最难查的 bug 就出在这里：**chunk 必须先变成 `PUBLISHED`，描述符才能进环**。反过来写会留下一个窗口：消费者已经从环里取走了描述符、把块改成 `CONSUMED`，而生产者的 CAS 要么失败，要么更糟——踩在另一个生产者刚借走的块上，把活消息的所有权标记清掉。它只在并发压力大时复现，每几十万条消息一次。现在 `ty_publish()` 先做状态转换，入环失败再回滚。

## 5. 通知与丢失唤醒协议

三种策略：spin、futex、hybrid（默认）。

协议部分值得读两遍：

```
等待方：   waiters++  ─栅栏─►  重查队列  ─栅栏─►  futex_wait
生产方：   enqueue    ─栅栏─►  读 waiters  ──►  必要时 futex_wake
```

因为重查发生在注册**之后**：一个读到 `waiters == 0` 的生产方，必然是在我们递增之前就入环了，所以重查不可能漏掉它的消息。读到 `>= 1` 的生产方则保证会唤醒。漏掉重查，你会得到每几十亿条消息挂一次的那种死锁。`ty_wait_for_msg()` 把三步都包在自己里面，就是为了把这个不变式放在一处。

第二个优化：**没人等待时完全跳过系统调用**。饱和流上这决定了吞吐，因为一次 futex 往返比整个发布路径还贵。

## 6. 崩溃安全

`SIGKILL` 不可捕获——没有 `atexit`，没有析构，没有清理。所以所有权是**租借**的，不是持有的。完整说明见 [CRASH-SAFETY_CN.md](CRASH-SAFETY_CN.md)，三层概括：

| 层 | 机制 | 防什么 |
|---|---|---|
| 1 | 每进程心跳时间戳 | 区分"慢"和"死了" |
| 2 | 每个 chunk 的租约 deadline | 限定最多能失踪多久 |
| 3 | 控制面的 robust 进程间互斥锁 | 进程**拿着锁**死掉时怎么恢复 |

恢复不只信时间。只有能证明没人还要用这块内存时才回收：owner 已被确认消失，或者租约到期**且**心跳停止推进——因为从慢但活着的生产者手里抢块，等于破坏活数据。

## 7. 顺序契约

```
partition = mix64(key) & (partitions - 1)
```

同 key 进同分区，严格 FIFO。不同 key 可并行消费，彼此无顺序保证。这是并行的代价，写在 README 里而不是悄悄违反。

## 8. 明确不做的事

- **不支持动态扩容。** region 和池在创建时定大小。负载中扩容意味着要么全局停等重映射，要么开第二个映射，对目标场景都不值。
- **默认不开后台线程。** 回收器是可选的（`spawn_reaper`），另外提供了 `tachyond` 给想用独立进程做回收的人。默默起线程的库会在 `fork()` 时给人惊喜。
- **不做跨机。** 这是 IPC。要网络透明就在上面套真正的 RPC。
- **没有安全模型。** 能附加就能读全部。安全边界用 `/dev/shm` 的文件权限。
